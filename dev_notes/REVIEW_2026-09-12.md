### 2.1 `37b23b8` - control.c `static __thread` scratch -> `ctrl_scratch_t` on the stack

**Verdict: behaviour-preserving. No finding.**

- **Lifetime/scoping.** `ctrl_scratch_t sc` is declared in `control_apply_json()` (control.c:697) and outlives every callee that receives `&sc`: `apply_ctrl_fields` -> `timps_apply_setting` -> `echo_add`/`defer_add`, and `ign_scan` -> `ign_note` -> `ign_add`. No callee stores the pointer; the result is copied out into `res` (control.c:1050-1060) before `sc` goes out of scope. No stale-pointer path.
- **No recursion / aliasing.** `timps_apply_setting` is called only from `apply_ctrl_fields` and three direct sites in `control_apply_json` (control.c:606, 739, 740, 827); `control_apply_json` has exactly one external caller (httpd.c:1956) and is serialized by `apply_mu` (control.c:707-708). There is therefore never more than one live `ctrl_scratch_t` at a time; the per-thread isolation the TLS statics gave is a strict subset of what the stack local gives.
- **Zero-init equivalence.** Old code reset only `g_*[0]=0`, the offsets and the three `*_full=1` flags per call (the TLS block itself was zero on thread start). New code does `= {0}` for the whole struct and then sets the same three `*_full = 1` (control.c:697-698) - equal or stricter.
- **Completeness.** `grep -n 'g_acc\|g_chg\|g_rej\|g_nopersist\|g_echo\|g_defer\|g_ign\|g_deferred' src/control.c` -> **no hits**. grep is not preprocessor-gated, so every `#ifdef` block (`USE_PLAY`, `USE_DAYNIGHT`, `USE_RECORD`, `USE_TIMELAPSE`) is covered - a stale reference inside a block the sim build does not compile would have shown.
- **Stack budget.** `sizeof(ctrl_scratch_t)` = 512 + 1024 + 512 + 8 ints ~= 2.1 KB (`CTRL_*_CAP`, control.h:102-104) on `MS_STACK_CONN` = 256 KB (util.h:99). The big `ctrl_changes` array was already heap (`free(ch)`, control.c:1061). Not a concern.
- **T21 goal verified directly.** control.c compiled with the xburst1 uclibc toolchain (`toolchain/xburst1-uclibc/.../mipsel-linux-gcc`, `-DPLATFORM_T21`): `readelf -r control.o | grep -c TLS` = **0**. ### 2.2 `bcf39ae` - same-port HTTP/HTTPS via first-byte peek, `http.https` tri-state

**Verdict: correct and memory-safe; two Low robustness items (R1, R2), one policy Medium (R3), one Low parser item (R4). No new DoS vector (R5 analysis).**

Traced at httpd.c:1502-1533 (`conn_drop`, `peek_first_byte`), 1568-1603 (sniff in `conn_thread`), 2098-2131 (cap-503 path in `accept_thread`), 2195-2263 (`httpd_start`).

- **Peek vs. read race - none.** Only `conn_thread` reads `c->fd`; the peeked byte is left in the kernel buffer (`MSG_PEEK`) and consumed by either `mbedtls_net_recv` inside `ms_tls_accept()` (TLS path) or the existing header loop's `crecv()` (plain path, httpd.c:1633, preceded by a `poll()` that returns immediately because the byte is pending). The only concurrent actor is `httpd_stop()`'s `shutdown()` via the fd registry, which the sniff joins *after* `ms_creg_add` (httpd.c:1541) - a shutdown then surfaces as `POLLIN` + `recv()==0` -> `-1` -> `conn_drop`. Correct.
- **EINTR / partial read.** Both `poll()` and `recv()` retry on EINTR (httpd.c:1525, 1529). Exactly one byte is peeked, so TCP segmentation cannot split it. `POLLHUP`/`POLLERR` -> `pr>0` -> `recv` returns 0/-1 -> `-1`. `r==0` (EOF) is handled explicitly.
- **Urgent data.** `SO_OOBINLINE` is never set, so a TCP URG byte is *not* part of the in-band stream `MSG_PEEK` sees; `poll(POLLIN)` ignores `POLLPRI`. A client sending only an OOB byte simply waits for the sniff deadline. Not a misclassification vector.
- **Classification.** `0x16` is the TLS handshake record type for every SSL 3.0+/TLS version; HTTP method bytes are ASCII letters (>= 0x41). No overlap. SSLv2-style hellos (`0x80`) and garbage fall to the plain path and die in the header parser as before.
- **Cleanup on every exit path.** `conn_drop()` = `ms_creg_del` -> `close` -> `free` -> `g_nconn--` (httpd.c:1508-1515), i.e. the `done:` label (2047-2058) minus `ms_tls_close`, and every path that calls it has `c->tls == NULL` by construction (silent, handshake-failed, 426). Each such path `return`s immediately after - no double close, no leak. The cap-503 path in `accept_thread` never allocates `hconn` and closes `fd` unconditionally (2131).
- **Non-TLS build byte-identical.** `peek_first_byte`, `conn_drop` and the whole sniff are inside `#ifdef USE_TLS`; with `USE_TLS` and `http.https=0` there is no `tls_ctx`, so `conn_thread` skips the block. **Confirmed live**: cam-db (192.168.10.145, T31, `v1.9.11`, `tls.https=0`) closes a silent client, a `G`-then-stall client, a 4 s-silent-then-`G` client, and a `0x16`-then-stall client all at **5.00 s** - the pre-existing header deadline, unchanged.
- **Consumers of the tri-state (in this repo).** `conn_thread` (`>= 2` strict, 1587), `accept_thread` (`< 2`, 2113), `httpd_start` (truthiness for ctx build + the two-mode LOGI, 2195/2256-2262), `control_get_json` `tls.https` raw echo (control.c:1849-1856) and the `talk_ws==1 && !http_https -> 0` capability report (control.c:1446), the `/talk` 426 gate which is **per-connection** (`!c->tls && talk_ws < 2`, httpd.c:2024 - so a plaintext connection on an `https=1` port cannot reach `/talk` in the clear when `talk_ws=1`), the startup warning (`talk_ws==1 && !tls_port`, 2226-2243). All consistent. `http.https` has flags `0` -> File-only, matching the docs.
- **Consumers in `thingino-firmware-LuFi/package/timps/` (not this repo, checked because the task asked).** Correct: `S95timps` (`1|2|true|yes|on`), `S96onvif_discovery`, `agent-adapter`, `www/x/timps-token.cgi`, `www/preview.html` (`scheme==="both"` -> page scheme). **Incorrect: `files/timps-selftest.sh:15` and `files/www/x/timps-imp.cgi:27` match only `1|true|yes|on`** -> on `http.https=2` both dial plaintext and receive the 426 (R6).
- **Size.** T31 uclibc `-Os`, `USE_TLS`: `httpd.o` text 25,164 -> 26,148 B (**+984 B**); `config.o` unchanged. Net for tonight ~ **+720 B** text.

### Details on the items that need a decision

**B1 - `/talk` TLS busy-spin (Medium, stability, post-auth).** `ms_tls_read()` (tls.c:311-318) returns `0` for `MBEDTLS_ERR_SSL_WANT_READ/WRITE` and also passes through mbedTLS's own `0`, which `mbedtls_ssl_read()` returns when the underlying transport was closed *without* a `close_notify` (documented contract; the firmware links mbedtls 3.6.6). `ws.c:io_read` (187-201) maps every `0` to `errno=EAGAIN, return -1`; `read_exact` (278-306) then `continue`s into `poll_readable()`, which returns `WS_OK` immediately because a FIN'd TCP socket is permanently `POLLIN`. Result: a tight loop with no sleep until the 1 s frame deadline fires `WS_AGAIN`, after which `talk_ws.c:284-296` re-enters the same spin, until either `TALK_IDLE_MS` (10 s) elapses or a 3 s `ws_send_ping` fails with EIO. A killed browser tab, a WiFi drop or an RST therefore pins the single-core SoC for roughly 3-10 s per event, and can outlast `httpd_stop()`'s 500 ms drain (`MS_HTTP_DRAIN_MS`), forcing its "leak `tls_ctx`/`h`" path (httpd.c:2307-2321). Reachable only after authentication (the unauthenticated 401/403 paths never reach `ws_read_message`), so **stability, not a remote DoS** - but `talk_ws=1` (the default on-mode) *only* allows the TLS path, so this hits every real-world disconnect. The plain-`read()` path is fine (`0` -> `WS_CLOSED`). I confirmed the httpd side is *not* affected: every streaming-loop `crecv()` uses `MSG_DONTWAIT` (which returns `-1` over TLS, httpd.c:222-232) and the two blocking loops `break` on `<= 0` (1634, 1878). *Fix scope:* either make `ms_tls_read()` return `-1` for `mbedtls_ssl_read()==0` (treat transport EOF like `close_notify`; the crecv consumers already handle `<0`), or disambiguate in `io_read` with `recv(fd,&b,1,MSG_PEEK|MSG_DONTWAIT)==0`. One function either way.

**R3 - semantic widening of an existing security setting (Medium, policy).** Before `bcf39ae`, `http.https=1` (and its bool spellings) meant "this port is TLS-only; a plaintext client gets nothing". After it, the same stored value means "plaintext is served too" (httpd.c:1601 fall-through), i.e. every Basic/Digest header and `?token=` a client chooses to send in the clear is now accepted on the port the operator configured for TLS. The `T_TRISTATE` rule "bool words -> 1" (config.c:1268-1273) is the *right* rule for `audio.talk_ws` (where 1 is the stricter mode) and the wrong one here, which the comment at config.c:839-841 openly acknowledges. This is announced by CHANGELOG and by the boot LOGI at httpd.c:2256-2262; there is no LOGW, no migration, and a WebUI that follows the page scheme will happily use `http://`. The firmware now *ships* `1` (timps.mk) so the default is deliberate; the question is only existing hand-configured `1`/`true` installs. Whether the trade (preview works from either page scheme) is worth it is the operator's call; from a review standpoint the change should be **loud for a release**: a one-shot `LOGW` when `http_https==1` was read from the file (not defaulted), or mapping the legacy bool spellings `true/on/yes` to `2` while the digit `1` takes the new meaning. *Fix scope:* config.c `T_TRISTATE` case (per-field flag) or one LOGW in `httpd_start`.

**R1 - 426/503 followed by `close()` with unread request data (Low).** On the 426 path (httpd.c:1592-1599) the client's whole request line is still in the receive buffer when `conn_drop()` closes the fd; Linux then emits an RST rather than a FIN. Linux/macOS clients typically still deliver the already-queued 426 bytes, Windows stacks discard pending data on RST - so the "say why instead of making the operator tcpdump" intent (comment at 1588-1591) is not reliably achieved on every client. Same shape on the cap-503 (2126-2131) when the peer already sent its request. *Fix scope:* before `close()`, `shutdown(fd, SHUT_WR)` and drain with a short bounded `recv` loop (the nginx `lingering_close` pattern), or read the header block first (it is bounded by the 4 KB buffer and the 5 s deadline anyway).

**R2 - sequential deadlines (Low).** `hdr_deadline` is computed at httpd.c:1619 *after* the sniff returns, so on `https>=1` a client may sit silent 4.9 s, send one byte, then trickle for another 5 s: ~10 s per slot versus 5 s on `https=0`. Still bounded and still below the old TLS-only 30 s; noted for completeness. *Fix scope:* take `t0` before the sniff and derive both deadlines from it.

**R4 - silent fail-open on a mistyped security key (Low).** `pbool()` (config.c:82) returns 0 for anything but `1/true/on/yes`; `pint_cl()` (90-96) clamps `strtol` output, and `strtol("strict")` is 0. So `http.https = strict`, `http.https = ture`, `rtsp.tls = enabled` all quietly become plaintext, logged only as "listening on port 8880". The clamping design is documented and intentional (config.c:86-89, prior audits M11) for *numeric* keys where a bad value would brick the stream; for a security bool it fails **open**. The tri-state sharpens this because the documented way to keep the old strict behaviour is now the digit `2`. *Fix scope:* a `LOGW` in `field_set()` for `T_BOOL`/`T_TRISTATE` when the value is neither a bool word nor a digit in range (a few lines, applies to all such keys).

**R5 - DoS surface of the sniff (Info, no finding).** Pending-classification connections are counted in `g_nconn` at accept (httpd.c:2143), so they are capped by `HTTP_MAX_CLIENTS` (16). Worst-case hold per silent slot: `https=0` 5 s (unchanged); `https>=1` 5 s (was **30 s**, the handshake cap, for the old TLS-only `1`); `0x16`-then-stall 30 s (unchanged, `MS_TLS_HANDSHAKE_S`). Sustaining a full 503 therefore costs an attacker ~3.2 new connections/s - the pre-existing slot-exhaustion class (H2 lineage, mitigated by timeouts since 07-18), not a new one. The cap-503 peek is non-blocking (`poll` timeout 0, 2112) and never parks the accept loop.

**B2 - `fanqueue_init` cap 0 (Low).** `45aec8a` made `MS_MJPEG_QCAP` a documented `-D` knob; `fanqueue_init` does not reject `cap<1` (fanqueue.c:18-22), and the first `fanqueue_push` would divide by zero. One-line guard.

1. **B1** - `/talk` TLS EOF spin (one-function fix in `ms_tls_read()` or `io_read()`); the only item with a measurable operational effect on the current fleet once `/talk` is used.
